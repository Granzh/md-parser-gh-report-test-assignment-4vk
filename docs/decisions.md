# Принятые решения

Правило: правила ТЗ приоритетнее примеров. Каждое решение фиксируется тестом.

| Проблема | Решение | Почему | Тест |
|----------|---------|--------|------|
| UTF-8: что считать некорректным (3.3, 3.6) | `decode_utf8` строгий: отвергает одиночные 0x80-0xBF, C0, C1, F5-FF, overlong, суррогаты, > U+10FFFF, оборванные и неверные продолжения; NUL, U+FEFF и управляющие символы допустимы, нормализации нет | Единственная ошибка библиотеки — invalid_utf8, терпимый декодер скрыл бы её; BOM нельзя терять, иначе сдвинутся позиции диапазонов | `test_utf8`: `decode_rejects_*`, `decode_empty_nul_bom_and_controls`, `roundtrip_all_code_points` |
| «Буква или цифра» в правиле 3 не определено точно | `is_letter_or_digit` — таблица отсортированных интервалов (категории L* и Nd) без `<locale>`/ICU; комбинирующие знаки (Mn/Mc, в т.ч. матры, тайские гласные) и письменности вне списка (эфиопская, кхмерская, лаосская, тибетская, мьянманская и др.) НЕ входят; полный перечень в контракте функции | Точное соответствие Unicode потребовало бы полной базы; выбран переносимый приближённый набор, ограничения явно задокументированы | `test_charclass`: `letter_digit_representatives_per_script`, `..._negative_examples_...`, `..._both_sides_of_every_table_boundary`, `table_is_sorted_disjoint_...` |
| Контракт для определений в `.cpp` | Полный Doxygen-контракт лежит у объявления в заголовке; определение в `.cpp` помечено `// NOLINT(contract) documented in <header>`; внутренние функции без заголовка документируются полностью | Не дублировать один и тот же контракт в двух местах (расхождение копий хуже его отсутствия) | `contracts_lint` в ctest |
| `main` и `--check-covers` | Линтер не требует `covers:` для C++-функции `main` | Командная строка проверяется сквозными тестами (часть 3), модульно `main` не вызвать | `test_cpp_function_refs_skip_main` (tools) |
| Санитайзеры на Windows | `MSGFMT_SANITIZE` проверяется в WSL Fedora (g++ 14, cmake 3.30): `cmake -S msgfmt -B build -DMSGFMT_SANITIZE=ON -DMSGFMT_WERROR=ON && ctest`; на Windows mingw g++ не имеет санитайзеров, а clang собирается, но любая программа с перехваченным исключением падает в ASan (воспроизводится на 10 строках без кода проекта) | Дефект инструментария, а не проекта | ctest в Fedora: все тесты зелёные без сообщений санитайзеров |
| Пример 9 и правило 10: `**жирный _и курсив_**` и `**жирный _и_ курсив**` | Правила приоритетнее таблицы. `**жирный _и курсив_**` даёт bold(0,15) + italic(7,8); `**жирный _и_ курсив**` даёт bold(0,15) + italic(7,1). Реализовано по правилам, тестируются оба входа | Строка из правила 10 по правилам не может дать italic(7,1) | `test_parser`: `decision_a1_example9_both_variants` |
| Закрывающий маркер (правило 5): что значит «ближайший подходящий» | Ищется в сыром тексте внутри границ внешнего среза; экранированный символ (`\x`, где x служебный) маркером не считается; code-span при поиске внешнего закрывающего НЕ учитывается; внутри code экранирования нет, закрывает ближайшая обратная кавычка с непробельным символом перед ней. Содержимое пары разбирается рекурсивно только внутри пары, поэтому частичные пересечения невозможны. `**a _b** c_` → текст `a _b c_`, bold(0,4); ``**a `x**y` b**`` → текст ``a `xy` b**``, bold(0,4); `_a **b_ c**` → текст `a **b c**`, italic(0,5) | Буквальное чтение правил 1, 5, 7, 12; иначе потребовался бы возврат назад (не однопроходный разбор) | `test_parser`: `decision_a2_*` |
| Пустое содержимое (`****`, ``` `` ```, `__`) | Закрывающий маркер должен стоять после хотя бы одного символа содержимого; иначе конструкция не замкнута и её символы выводятся как обычные (правило 6). Диапазонов нулевой длины не бывает. `****`, ``` `` ```, `__` → без диапазонов, текст равен входу | Правила не запрещают пустое содержимое явно (в отличие от ссылки), но «непробельный символ перед закрывающим» не должен быть самим открывающим маркером | `test_parser`: `decision_a3_empty_content_is_literal` |
| Тройные и смешанные маркеры | `***a***` → текст `*a*`, bold(0,2) (закрывает ближайшая пара `**` после `a`, лишняя `*` — литерал; одиночная `*` маркером не является); `**_a_**` → bold(0,1), italic(0,1); `_**a**_` → italic(0,1), bold(0,1); `__a__` → текст `_a_`, italic(0,2). Не открывшийся `**` выводится двумя литералами | Токен открытия — именно `**`; порядок — по правилу 12 | `test_parser`: `decision_a4_*` |
| Ссылка: вложенность, `[`, `\]`, url | Внутри текста ссылки стили разрешены (правило 10); `[` в тексте — литерал, т.к. стиль link уже открыт (побеждает внешняя ссылка слева); текст заканчивается на первом неэкранированном `]`, `\]` даёт `]`; перед `]` обязан стоять непробельный символ (правило 5), иначе литералы; `(` обязана идти сразу за `]`; url берётся как есть (экранирование не действует, `[a](u\)` → url `u\`), непустой, без пробельных Unicode-символов и `)`. link в bold и bold в link — по порядку открытия | Правило 8 + правила 5, 9, 10 буквально | `test_parser`: `decision_a5_*` |
| Правило 3 (`_`) на границах | «Предыдущий символ» — сырой символ входа; «начало текста» — только индекс 0 всего входа (начало вложенного среза предваряется маркером, то есть границей слова). `\_a_` → литералы (`_a_`); `a\__` → `a__`; перед `_` эмодзи — граница (не буква/цифра), цифра и кириллица — не граница; закрывающий `_` перед эмодзи допустим | Правило 3 + решение по charclass | `test_parser`: `decision_a6_*` |
| `\` в конце входа и перед обычным символом | Одиночный `\` в конце — обычный символ; `\` перед не служебным символом сохраняется вместе с ним | Правило 9 | `test_parser`: `decision_a7_*` |
| Идентичные интервалы разных стилей | Порядок по правилу 12: первым идёт стиль, открытый раньше во входе (внешний); порядок открытия фиксируется в момент открытия маркера | Правило 12 | `test_parser`: `decision_a8_*`; `test_parser_internal`: `sort_ranges_*` |
| `parse` и недопустимые скалярные значения в `u32string` | `parse` тотальна: суррогаты и значения > U+10FFFF заменяются на U+FFFD (одна кодовая единица UTF-16); исключений нет, кроме `std::bad_alloc` | Кодирование недопустимого значения нарушило бы предусловие `encode_utf8_append` | `test_parser`: `parse_replaces_invalid_scalar_values` |
| Формат JSON (разд. 3.6) | Компактный, без пробелов; порядок полей фиксирован: `text`, `ranges`; внутри диапазона `style`, `offset`, `length`, `url`; ровно эти поля. Экранирование строк: `"`→`\"`, `\`→`\`, `\b \f \n \r \t`, остальные U+0000-001F → `\u00xx` с НИЖНИМ регистром hex; `/`, DEL, не-ASCII и U+2028/2029 выводятся как есть | ТЗ не фиксирует порядок и регистр; компактный вид проще сравнивать; U+2028/2029 допустимы в JSON | `test_json`: `json_escape_*`, `to_json_*` |
| Завершающий перевод строки | Ни JSON, ни результат `escape` не получают добавочного `\n` (вывод — ровно байты результата) | `escape` должен возвращать исходный текст без добавок (`printf '2 * 3' \| msgfmt escape` → `2 \* 3`); одинаково для JSON | `test_cli`: `run_*`, `test_cli_process`: `process_*` |
| Код возврата при неверных аргументах | `64` (EX_USAGE): usage в stderr, stdout пуст, stdin не читается. Любые аргументы, кроме отсутствия или единственного `escape`, — ошибка (включая `--help`). Внутренняя ошибка (исключение, сбой ввода-вывода) — `70` | ТЗ определяет только 0 и 2; 64/70 — общепринятые коды sysexits, не пересекаются с 0 и 2 | `test_cli`: `run_usage_errors_*`, `run_reports_internal_errors_*`; `test_cli_process`: `process_usage_error` |
| Ввод-вывод в бинарном режиме | stdin читается целиком побайтно; на Windows `main` переключает stdin/stdout в бинарный режим (`_setmode`), иначе `\r\n`/NUL искажались бы | Правило 3.3: управляющие символы и переводы строк не преобразуются | `test_cli_process`: `process_keeps_crlf_and_nul_bytes` |
| Невалидный UTF-8 в режиме `escape` | Тот же ответ, что и при разборе: `{"error":"invalid_utf8"}`, код 2 | Разд. 3.6 | `test_cli`: `run_escape_mode_invalid_utf8_*` |
