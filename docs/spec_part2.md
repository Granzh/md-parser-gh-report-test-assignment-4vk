Часть 2. Служба ghreport (Go, Docker) 
4.1. Назначение

Служба ghreport формирует сводку по открытым issue указанных репозиториев GitHub. Сводка предназначена для регулярного обзора, поэтому служба обязана корректно работать с постраничной выдачей, условными запросами, ограничениями частоты запросов и сбоями отдельных репозиториев.

4.2. Синтаксис командной строки

ghreport --repos <owner/repo[,owner/repo...]>

         [--limit <N>] [--since <YYYY-MM-DD>]

         [--out <file|->] [--trace <file>] [--cache-dir <dir>]




При некорректных аргументах выводится сообщение в stderr, стандартный вывод остаётся пустым, код возврата - 2.

Адрес API и токен читаются из окружения процесса: они не встраиваются ни в код, ни в образ. Если переменная GITHUB_API_BASE_URL не задана, используется адрес по умолчанию; если задана - служба обязана обращаться именно по указанному адресу, в том числе при запуске в контейнере.

4.4. Обмен с API
Служба обращается к единственному эндпоинту - списку issue репозитория. Все запросы выполняются последовательно, без параллельных обращений.

4.4.1. Формирование запроса

Метод и путь: GET {base}/repos/{owner}/{repo}/issues.

Параметры строки запроса: state=open, sort=created, direction=asc, per_page=100.

Заголовки: Accept: application/vnd.github+json; User-Agent с осмысленным значением (описывается в README); X-GitHub-Api-Version: 2026-03-10; Authorization: Bearer <token> при наличии токена.

Перенаправления 301, 302, 307 обрабатываются по документации GitHub.

Таймаут одного запроса - не более 30 секунд.

Пример адреса первого запроса (для наглядности разделён на две строки):

GET https://api.github.com/repos/cli/cli/issues

    ?state=open&sort=created&direction=asc&per_page=100


4.4.2. Постраничная выдача

Адрес следующей страницы берётся из заголовка Link ответа, из части rel="next"; адреса страниц вручную не конструируются.

Порядок работы: запросить очередную страницу; включить подходящие элементы; если набрано limit элементов или части next нет - остановиться; иначе перейти по адресу из Link и повторить.

Порядок элементов сохраняется: по возрастанию created_at, затем по number.

Пример заголовка Link (адреса сокращены):

link: <...?per_page=100&page=2>; rel="next", <...?per_page=100&page=7>; rel="last"


4.4.3. Фильтрация и дедупликация

Из элементов исключаются pull request-ы: признак - наличие ключа pull_request.

При заданном --since исключаются элементы с created_at меньше начала указанной даты (UTC). Фильтр выполняется службой: параметр since API не используется, так как он фильтрует по дате обновления, а не создания.

Элементы с одинаковым number включаются в отчёт один раз: если запись встречается на нескольких страницах, служба устраняет повтор дедупликацией.

4.4.4. Кэширование

Для каждого адреса служба сохраняет заголовок ETag и тело успешного ответа в каталоге --cache-dir.

При повторном запросе того же адреса отправляется заголовок If-None-Match с сохранённым значением.

Ответ 304 Not Modified: тело берётся из кэша, в журнал записывается from_cache: true.

Ответ 200: кэш обновляется, в журнал записывается from_cache: false.

Кэш переживает перезапуски процесса и не содержит токен.

4.4.5. Ограничения частоты и повторные попытки

Признаки исчерпания лимита: коды 403 или 429; при этом в теле сообщается об исчерпании лимита, либо присутствует заголовок retry-after, либо x-ratelimit-remaining равен нулю.

Пауза перед повтором: по значению retry-after; иначе - до времени x-ratelimit-reset (UTC, epoch); иначе - не менее 60 секунд.

Сетевые ошибки и ответы 5xx: до трёх повторных попыток на запрос с задержками 1, 2 и 4 секунды.

После исчерпания повторов репозиторий получает код ошибки, обработка переходит к следующему репозиторию.

4.4.6. Ошибки и коды возврата



Коды ошибок репозитория: not_found (ответ 404), rate_limited (исчерпание лимита), request_failed (сетевые ошибки или 5xx после повторов), invalid_response (ответ не является корректным JSON).

4.5. Формат отчёта
Отчёт - один JSON-объект UTF-8 следующей схемы:

{

  "generated_at": "<UTC, RFC3339>",

  "repos": [

    {

      "repo": "<owner/repo>",

      "error": <null | "not_found" | "rate_limited" |

                         "request_failed" | "invalid_response">,

      "count": <целое число>,

      "issues": [

        {

          "number": <целое число>,

          "title": "<строка>",

          "author": "<login>",

          "labels": ["<строка>", ...],

          "created_at": "<RFC3339, как в ответе API>",

          "url": "<html_url>"

        }

      ]

    }

  ]

}


Порядок репозиториев - как в аргументе --repos.

Массив issues отсортирован по created_at, затем по number (возрастание); count равен длине массива.

Поле error равно null при успешной обработке репозитория.

4.6. Журнал (--trace)
Формат JSON Lines: одна строка на каждую попытку HTTP-запроса, в порядке выполнения.

Поля записи: ts (RFC3339, UTC), method, url (полный адрес), status (код ответа; 0 при отсутствии ответа), attempt (номер попытки, начиная с 1), from_cache (истина при использовании данных кэша по ответу 304), error (null или краткое описание, например timeout или network).

Заголовок Authorization в журнал не записывается.

4.7. Стандартный вывод и журналирование
В стандартный вывод попадает только отчёт либо фатальный JSON-объект; диагностика направляется в стандартный поток ошибок.

Токен не попадает ни в stdout, ни в stderr, ни в журнал.

4.8. Контейнеризация
В каталоге service/ размещаются Dockerfile и .dockerignore.

Сборка и запуск: docker build -t ghreport service/; docker run --rm -e GITHUB_TOKEN=... ghreport --repos cli/cli --limit 20 --out -.

Переменные окружения передаются контейнеру при каждом запуске (флаг -e) и не вшиваются в образ. В примере указан только токен: GITHUB_API_BASE_URL не задан, потому что по умолчанию используется публичный адрес https://api.github.com. При работе с другим сервером, совместимым с контрактом, адрес передаётся тем же способом, например: docker run --rm -e GITHUB_TOKEN=... -e GITHUB_API_BASE_URL=<адрес сервера> ghreport --repos cli/cli --out -.

Контейнер запускается от непривилегированного пользователя (инструкция USER); секреты в образ не вшиваются; служба не зависит от файлов на хосте.

Б.2. Журнал
В файле каждая запись занимает одну строку; ниже строки перенесены для наглядности.

{"ts": "2026-10-14T09:00:01Z", "method": "GET",

 "url": "https://api.github.com/repos/cli/cli/issues?per_page=100",

 "status": 200, "attempt": 1, "from_cache": false, "error": null}

{"ts": "2026-10-14T09:00:02Z", "method": "GET",

 "url": "https://api.github.com/repos/cli/cli/issues?per_page=100",

 "status": 304, "attempt": 1, "from_cache": true, "error": null}


Б.3. Работа кэша
Первый запуск: страницы выдаются с кодом 200, в журнале у всех запросов from_cache: false.

Второй запуск с тем же --cache-dir: те же адреса получают 304, в журнале from_cache: true, отчёт совпадает с первым запуском.

Б.4. Ошибки
stdout: {"error": "unauthorized"}

stdout: {"error": "all_failed"}

stderr: ghreport: --limit должен быть целым числом, не меньшим единицы
