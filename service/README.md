# ghreport — сводка открытых issue GitHub (Go)

`ghreport` формирует JSON-сводку по открытым issue (без pull request) указанных репозиториев: постраничная выдача по
заголовку `Link`, условные запросы с кэшем на диске (`ETag`), ограничения частоты запросов, повторы при сбоях,
журнал HTTP-обмена. Только стандартная библиотека Go (`net/http`), без SDK GitHub и без сторонних модулей.
Репозитории читаются только на чтение (единственный эндпоинт — `GET /repos/{owner}/{repo}/issues`).

## Запуск

### Локально (Go ≥ 1.22)

```
cd service
go build -o ghreport ./cmd/ghreport
GITHUB_TOKEN=... ./ghreport --repos cli/cli --limit 20 --out -
```

Токен необязателен (без него действует низкий лимит анонимных запросов).

### В Docker

```
docker build -t ghreport service/
docker run --rm -e GITHUB_TOKEN=... ghreport --repos cli/cli --limit 20 --out -
```

Другой сервер, совместимый с контрактом GitHub (адрес используется ровно тот, что указан; `localhost` контейнера —
это сам контейнер, поэтому для сервера на хосте нужен `host.docker.internal`):

```
docker run --rm \
  --add-host=host.docker.internal:host-gateway \
  -e GITHUB_TOKEN=... \
  -e GITHUB_API_BASE_URL=http://host.docker.internal:8765 \
  ghreport --repos octo/demo --out -
```

Файлы (`--out`, `--trace`, кэш) в контейнере пишутся в рабочий каталог `/work` (доступен пользователю контейнера) либо
в смонтированный том: `-v "$PWD/out:/work/out" ... --out out/report.json`. Кэш между запусками контейнеров
сохраняется только если смонтировать `/work/.ghreport-cache` или задать `--cache-dir` на смонтированный каталог.

**Образ.** Многоэтапная сборка: `golang:1.22` (`CGO_ENABLED=0`, `-trimpath`, `-ldflags "-s -w"`) →
`gcr.io/distroless/static-debian12:nonroot`. Distroless выбран вместо alpine: в нём уже есть корневые сертификаты
(HTTPS к `api.github.com`), нет shell и пакетного менеджера, пользователь `65532` создан заранее. В `Dockerfile`:
`USER 65532:65532`, `ENTRYPOINT ["/ghreport"]` в exec-форме (аргументы `docker run … --repos …` доходят до службы),
нет ни одного `ENV`/`ARG` для токена или адреса — секреты в слоях образа отсутствуют.

## Параметры и переменные окружения

Командная строка:

```
ghreport --repos <owner/repo[,owner/repo...]>
         [--limit <N>] [--since <YYYY-MM-DD>]
         [--out <file|->] [--trace <file>] [--cache-dir <dir>]
```

| Параметр | По умолчанию | Описание |
|----------|--------------|----------|
| `--repos` | — (обязателен) | Репозитории через запятую, `owner/repo`, символы `[A-Za-z0-9._-]`. Дубликаты (точное совпадение строки) удаляются, остаётся первое вхождение. Пустые элементы, пробелы, лишние `/`, `.` и `..` — ошибка |
| `--limit` | `100` | Максимум issue на репозиторий; целое ≥ 1 (только цифры) |
| `--since` | — | Только issue, созданные не раньше `YYYY-MM-DD 00:00:00 UTC`; строго такой формат и существующая дата |
| `--out` | `-` | Файл отчёта; `-` — стандартный вывод. Файл пишется атомарно, недостающие каталоги создаются |
| `--trace` | — | Файл журнала HTTP-обмена (JSON Lines); при каждом запуске усекается; без параметра журнал не ведётся |
| `--cache-dir` | `./.ghreport-cache` | Каталог кэша; создаётся автоматически |
| `-h`, `--help` | | Справка в stderr, код 0 |

Позиционные аргументы и неизвестные параметры — ошибка (код 2). Повтор параметра: побеждает последнее значение.
Пустое значение `--out`, `--trace`, `--cache-dir` — ошибка.

Переменные окружения (других нет):

| Переменная | Назначение |
|------------|------------|
| `GITHUB_TOKEN` | Необязательный токен; передаётся как `Authorization: Bearer <token>` и только на адрес API (см. [безопасность](#безопасность-токена)). Пробелы по краям срезаются |
| `GITHUB_API_BASE_URL` | Базовый адрес API; по умолчанию `https://api.github.com`. Используется ровно он: схема `http`/`https`, есть host, завершающие слэши срезаются, префикс пути (`/api/v3`) сохраняется; user info, `?` и `#` недопустимы |

### User-Agent

`ghreport/1.0 (+учебный проект; read-only сводка issue)` (константа `httpx.DefaultUserAgent`). GitHub требует
осмысленный `User-Agent` и блокирует запросы без него; значение называет программу и версию и сообщает, что служба
только читает данные. Остальные заголовки: `Accept: application/vnd.github+json`,
`X-GitHub-Api-Version: 2026-03-10`, `If-None-Match` (при наличии записи кэша).

## Формат отчёта

Один JSON-объект UTF-8, отступ 2 пробела, завершающий перевод строки; `<`, `>`, `&` и не-ASCII не экранируются.

```json
{
  "generated_at": "2026-10-14T09:00:00Z",
  "repos": [
    {
      "repo": "cli/cli",
      "error": null,
      "count": 1,
      "issues": [
        {"number": 1, "title": "…", "author": "octocat", "labels": ["bug"],
         "created_at": "2026-01-05T10:00:00Z", "url": "https://github.com/cli/cli/issues/1"}
      ]
    }
  ]
}
```

(в реальном выводе объекты issue развёрнуты по строкам). Репозитории — в порядке `--repos`; issue отсортированы по
`created_at` (как момент времени), затем по `number`; `count` равен длине `issues`; `error` — `null` или один из
`not_found`, `rate_limited`, `request_failed`, `invalid_response`. `labels` и `issues` никогда не `null`.

## Архитектура

```
cmd/ghreport (main: сигналы, реальные зависимости)
        │
        ▼
   internal/app ── Run(ctx, args, deps, stdout, stderr) int
        │
        ├── args      разбор и проверка командной строки
        ├── config    GITHUB_API_BASE_URL, GITHUB_TOKEN
        ├── trace     журнал JSON Lines
        ├── cache     файловый кэш (ETag, Link, тело)
        ├── issues    Fetcher: страницы, фильтры, дедупликация, сортировка, ErrorCode
        │     ├── linkhdr   адрес следующей страницы из Link
        │     └── httpx     GET: заголовки, редиректы, повторы, лимиты  ── clock (все паузы)
        ├── model     структуры отчёта, JSON
        ├── exitcode  Summarize → код возврата
        └── output    запись отчёта (stdout / файл атомарно)

testutil — FakeGitHub для тестов (в продукт не входит)
```

Порядок обработки:

1. `args.Parse` → при ошибке сообщение в stderr, stdout пуст, на диске ничего не создаётся, код 2.
2. `config.FromEnv` → при ошибке код 2.
3. Открыть `--trace` (ошибка → код 2); создать каталог кэша (ошибка → предупреждение, работа без кэша).
4. Репозитории **строго последовательно** в порядке `--repos`. Для каждого `issues.Fetcher`: первый адрес
   `…/repos/{owner}/{repo}/issues?state=open&sort=created&direction=asc&per_page=100`; цикл «запись кэша → `httpx.Get`
   (`If-None-Match`) → разбор страницы → следующий адрес только из `Link`». Остановка: набран `--limit` (сразу, даже
   внутри страницы) либо нет `rel="next"`.
5. Элемент: есть ключ `pull_request` → пропуск; `created_at` раньше `--since` → пропуск; повтор `number` → пропуск.
6. Ошибка репозитория → код ошибки в отчёте, строка в stderr, следующий репозиторий. 401 → сразу фатально.
7. `exitcode.Summarize`, запись отчёта, код возврата.

Тесты не используют реальных пауз и сети: время и паузы идут через `clock.Clock` (в тестах `clock.Fake`), сервер —
`testutil.FakeGitHub` на `httptest`.

## Формат кэша

Каталог `--cache-dir`; по одному файлу на каждый запрошенный адрес.

* **Имя файла:** `<hex(sha256(полный исходный URL запроса))>.json` (64 hex-символа). Ключ — адрес первого хопа; при
  перенаправлениях ключом остаётся исходный адрес.
* **Содержимое:**

  ```json
  {"version":1,"url":"https://api.github.com/repos/o/r/issues?state=open&…","etag":"\"abc\"",
   "link":"<https://…&page=2>; rel=\"next\", <https://…&page=7>; rel=\"last\"","body":"[{…}]"}
  ```

  `version` — формат (сейчас 1); `url` — адрес запроса (защита от подмены файла); `etag` — как прислал сервер, слабые
  `W/"…"` хранятся как есть; `link` — все значения заголовка `Link`, склеенные через `, `; `body` — JSON-текст ответа
  строкой. Заголовки запроса и токен в файл не попадают.
* **Когда пишется:** только после ответа 200 с `ETag`, если тело — валидный UTF-8 JSON-массив. Без `ETag` или с не-массивом
  запись не создаётся.
* **Промах:** файла нет или он нечитаем; JSON повреждён; `version` ≠ 1; `url` в файле не совпадает с запрошенным;
  пустой `etag`. Паника исключена; при промахе запрос идёт без `If-None-Match`, а запись перезаписывается.
* **Использование:** запись есть → `If-None-Match: <etag>`. Ответ 304 → тело и `Link` берутся из кэша (`Link` из самого
  304-ответа приоритетнее, если он есть), в журнал `from_cache: true`. Ответ 304 без записи в кэше — `invalid_response`.
  Ответ 200 → запись обновляется.
* **Атомарность и права:** временный файл в том же каталоге + `rename`; каталог 0700, файл 0600. Ошибка записи кэша не
  фатальна — предупреждение в stderr.
* **Почему хранится `Link`:** адреса страниц вручную строить нельзя, а по ответу 304 сервер `Link` обычно не присылает.
  Без сохранённого `Link` повторный запуск после 304 первой страницы не нашёл бы вторую и отчёт был бы неполным.

## Лимиты, повторы и ошибки

Все паузы идут через `clock.Clock`. Запросы строго последовательны.

| Ситуация | Пауза перед повтором | Повторов | Результат после исчерпания |
|----------|----------------------|----------|----------------------------|
| 403/429 и (в теле «rate limit» без учёта регистра, **или** есть `Retry-After`, **или** `X-RateLimit-Remaining: 0`) | `Retry-After` (секунды или HTTP-дата); иначе до `X-RateLimit-Reset` (epoch, UTC), не менее 1 с; иначе 60 с. Не более 1 часа. Негативный/мусорный `Retry-After` игнорируется | 3 | `rate_limited` |
| сетевая ошибка, таймаут (30 с на запрос), 5xx | 1 с, 2 с, 4 с | 3 | `request_failed` |
| 401 | — | 0 | фатально: `{"error": "unauthorized"}`, код 3 |
| 404 | — | 0 | `not_found` |
| прочие 4xx, в т.ч. 403 без признаков лимита; прочие 3xx (кроме 304); 2xx кроме 200 | — | 0 | `request_failed` |
| тело не JSON-массив, нет/неверны обязательные поля, цикл в `Link`, слишком много страниц, 304 без записи кэша | — | 0 | `invalid_response` |

Два независимых бюджета по 3 повтора («лимит» и «сеть/5xx»). Перенаправления 301/302/307 — вручную по `Location`, не
более 5 переходов, только `http`/`https`; каждый переход — отдельная запись журнала. Размер ответа ограничен 64 МиБ.
Отмена (SIGINT/SIGTERM) прерывает паузы и запросы без повторов.

## Коды возврата

| Код | Ситуация | Вывод |
|-----|----------|-------|
| 0 | все репозитории успешно (а также `--help`) | отчёт |
| 1 | часть репозиториев с ошибкой | отчёт; у проблемных заполнено `error` |
| 2 | некорректные аргументы, окружение (`GITHUB_API_BASE_URL`) или недоступный `--trace` | сообщение в stderr, stdout пуст |
| 3 | ответ 401 | `{"error": "unauthorized"}` в stdout, отчёт не пишется, остальные репозитории не запрашиваются |
| 3 | все репозитории с ошибкой (в т.ч. единственный) | `{"error": "all_failed"}` в stdout; отчёт с ошибками записывается в `--out`, если это файл, а при `--out -` не выводится |
| 3 | отчёт не удалось записать | сообщение в stderr, stdout пуст |
| 130 | прервано SIGINT/SIGTERM | сообщение в stderr, stdout пуст, отчёт не пишется |

В stdout попадает только отчёт либо фатальный JSON; вся диагностика — в stderr.

## Журнал `--trace`

JSON Lines, одна строка на каждую HTTP-попытку (и каждый переход по редиректу) в порядке выполнения, запись сбрасывается
на диск сразу:

| Поле | Значение |
|------|----------|
| `ts` | время, RFC3339 UTC |
| `method` | всегда `GET` |
| `url` | полный адрес (user info удаляется) |
| `status` | код ответа, `0` если ответа нет |
| `attempt` | номер попытки логического запроса с 1 (растёт после любого повтора; переходы по редиректам несут тот же номер) |
| `from_cache` | `true`, только если ответ 304 на запрос с `If-None-Match` |
| `error` | всегда присутствует: `null`, `timeout`, `network`, `canceled`, `too_large` |

Заголовок `Authorization` и токен в журнал не записываются.

## Принятые решения

Полный перечень с привязкой к тестам — в [../docs/decisions.md](../docs/decisions.md). Главные:

* **Дубликаты в `--repos`** — точное совпадение строки, остаётся первое вхождение; `.`/`..` как owner/repo — ошибка.
* **`--help`** — usage в stderr, stdout пуст, код 0.
* **Строгий разбор `--limit`/`--since`** вручную (`flag.Int` принимает `+5`, `0x10`).
* **Родительские каталоги `--out` создаются**, запись атомарна.
* **`GITHUB_API_BASE_URL`** — используется ровно заданный адрес; ошибка не содержит ни адреса, ни токена.
* **Единственный репозиторий с ошибкой** → код 3, `all_failed`; при `--out -` отчёт в stdout не выводится.
* **Редиректы вручную** через `Transport.RoundTrip`, токен — только на тот же origin, что и `GITHUB_API_BASE_URL`.
* **Паузы при лимите:** потолок 1 час; `Retry-After: 0` допустим; отрицательные/мусорные значения игнорируются.
* **`Link` хранится в кэше** (см. выше).
* **Порядок проверок элемента:** PR → обязательные поля → `--since` → дубликат; невалидный issue ломает весь репозиторий
  (`invalid_response`), PR не проверяется.
* **Сигнал** → код 130, ошибка записи отчёта → код 3.
* **Doc-комментарии Go** пишутся с секциями `Args:`/`Returns:`/`Errors:` без отступа (так их не переписывает `gofmt`).

## Известные ограничения

* Работает только с эндпоинтом списка issue; GraphQL, поиск и статусы не используются.
* Нет параллелизма (требование ТЗ): много репозиториев — долго.
* Лимит в одну паузу ограничен часом; более долгий сброс лимита закончится `rate_limited` после трёх повторов.
* `limit` применяется к порядку выдачи сервера (`sort=created&direction=asc`) до итоговой сортировки.
* Кэш не чистится автоматически (по одному файлу на адрес); устаревшие файлы можно удалять вручную.
* Токен, разбитый на два вызова записи в stderr, не маскируется (сообщения пишутся целиком одним вызовом).
* `HTTP_PROXY`/`HTTPS_PROXY` учитываются стандартным транспортом Go; токен тогда видит прокси (как и в любом клиенте).

## Безопасность токена

* Токен читается только из `GITHUB_TOKEN`; не встраивается ни в код, ни в образ (в `Dockerfile` нет `ENV`/`ARG`).
* Заголовок `Authorization` отправляется только на origin (схема + host + порт) из `GITHUB_API_BASE_URL`; на другой хост —
  никогда, в том числе при редиректе.
* Токен не попадает в stdout, журнал, кэш и отчёт; весь stderr пропускается через `Scrub` (токен → `***`), тела ответов
  сервера в диагностику не включаются, тексты ошибок очищаются от токена.
* Тесты (`TestTokenNeverLeaks`) ищут «токен-страж» во всех выходах и файлах после ошибок и редиректов.
